# Kontra Digital Asset Layer — Product Implementation Brief

## Objective

Embed tokenization readiness into Kontra’s existing transaction workspace **without rebuilding the platform and without turning Kontra into an issuer, broker, exchange, custodian, or token marketplace**.

The existing architecture should remain intact:

**Create workspace → configure participants/documents/stages → coordinate transaction → verify requirements → close transaction**

The change is to make the final output of that process a **verified, structured transaction package that can support tokenization or other digital ownership infrastructure**.

Tokenization should not appear as a few isolated fields or a separate blockchain module. It should become a contextual layer that uses information already collected throughout the workspace.

---

# 1. Preserve the current platform architecture

Do not redesign or replace the existing:

* Workspace creation flow
* Workflow packs
* Participants
* Documents
* Tasks
* Activity timeline
* Operations Manager
* Transaction stages
* Role-based access
* AI document analysis
* Verified Transaction Package

Add a new internal module called:

> **Digital Asset Layer**

This module should consume data already generated by participants, documents, approvals, ownership records, jurisdiction settings, and the audit trail.

No blockchain deployment, wallets, minting, investor payments, custody, or secondary trading should be added in this phase.

---

# 2. Make Digital Asset Readiness optional per workspace

During workspace creation, add a field after transaction type:

### Digital asset preparation

Options:

* Not needed
* Evaluate readiness
* Preparing for tokenization

Default to **Not needed** for ordinary transactions.

When either readiness option is selected, reveal:

* Asset category
* Jurisdiction
* Intended ownership structure
* Fractional ownership: Yes / No / Undecided
* Intended issuance platform: Optional
* Target tokenization date: Optional

Do not require the user to choose a token standard during onboarding.

The user may not know whether ERC-3643, ERC-1400, another standard, or a non-blockchain registry will ultimately be used.

---

# 3. Make jurisdiction functional, not cosmetic

The jurisdiction selector should modify the workspace requirements.

Create a configurable jurisdiction-pack structure rather than hardcoding requirements into the frontend.

Initial jurisdiction options:

* UAE — ADGM
* UAE — DIFC
* UAE — VARA / Dubai
* United States
* European Union
* United Kingdom
* Singapore
* Other / Not specified

Each jurisdiction pack should define:

* Required entity information
* Beneficial ownership information
* Identity requirements
* Ownership documentation
* Investor-related requirements
* Legal review items
* Compliance items
* Required disclaimers
* Export metadata

Important: Kontra must display these as **configurable preparation checklists**, not legal conclusions.

Use language such as:

> Suggested based on the selected jurisdiction. Review with qualified legal, financial, and regulatory advisers.

Do not display “compliant,” “approved,” or “eligible to issue” solely because fields are complete.

---

# 4. Add an Ownership section

Ownership is the missing bridge between transaction coordination and tokenization readiness.

Add **Ownership** as a workspace tab when Digital Asset Readiness is enabled.

The section should capture:

### Asset owner

* Legal entity name
* Entity type
* Formation jurisdiction
* Registration number
* Registered address
* Governing documents
* Authorized representative

### Beneficial ownership

* Owner name or entity
* Ownership percentage
* Ownership type
* Direct or indirect ownership
* Verification status
* Supporting document

### Ownership structure

* Parent entities
* Subsidiaries
* Special-purpose vehicles
* Existing liens or encumbrances
* Transfer restrictions
* Rights attached to the ownership interest

### Cap table or ownership ledger

* Holder
* Class
* Units or shares
* Percentage
* Voting rights
* Economic rights
* Restrictions
* Effective date

The total ownership percentage should be validated against 100%, but the user must be allowed to save an incomplete structure.

Display:

* Complete
* Incomplete
* Needs review
* Conflicting information

Do not use “verified” unless there is supporting evidence and an identifiable verification event.

# 5. Add a Digital Asset Readiness panel to Overview

When readiness is enabled, add a card below the Operations Manager:

## Digital Asset Readiness

Show:

* Overall readiness percentage
* Documentation
* Ownership
* Entity verification
* Beneficial ownership
* Identity
* Legal review
* Compliance preparation
* Audit trail
* Structured data

Each category must show:

* Complete
* In progress
* Missing
* Needs review
* Not applicable

The score must be explainable. Users should be able to click a category and see exactly which requirements contributed to it.

Do not create an opaque AI-generated score.

Suggested calculation:

* Each jurisdiction pack defines requirement weights.
* Required items count toward the score.
* Optional items do not reduce the score.
* Conflicts or failed verifications reduce the relevant category.
* Missing required items prevent a “Ready” status.

Readiness labels:

* **0–39%: Foundation incomplete**
* **40–69%: Preparation in progress**
* **70–89%: Substantially prepared**
* **90–100%: Ready for professional review**

Never label the workspace “approved for tokenization” or “regulator-ready.”

# 6. Connect documents to readiness requirements

Each document type should support additional metadata:

* Readiness category
* Requirement satisfied
* Jurisdiction relevance
* Evidence type
* Verification status
* Expiration date
* Conflicting document references

Examples:

* Formation document → Entity verification

* Cap table → Ownership structure
* Passport or entity ID → Identity
* Beneficial-owner declaration → Beneficial ownership
* Valuation report → Asset information

* Legal opinion → Legal review
* KYC report → Identity/compliance preparation

On the Documents page, display a small contextual label such as:

> Contributes to: Ownership structure

or

> Required for: UAE — ADGM preparation

Do not make every ordinary transaction document display tokenization labels when readiness is disabled.

# 7. Add readiness-related tasks

The task engine should automatically generate tasks from missing readiness requirements.

Examples:

* Complete ownership structure
* Add all beneficial owners
* Upload governing documents
* Resolve ownership percentage discrepancy
* Confirm transfer restrictions
* Assign legal reviewer
* Select intended issuance jurisdiction
* Complete entity verification
* Review jurisdiction-specific requirements
* Confirm whether fractional ownership is intended

Tasks should follow the existing distinction between:

* Needs your attention
* Waiting on others
* Blocked
* Completed

The Operations Manager should prioritize readiness tasks only when they are relevant to the current transaction stage.

# 11. Digital Asset Manifest

Create a machine-readable JSON export with a versioned schema.

Suggested high-level structure:

```json
{
  "schema_version": "1.0",
  "workspace_id": "",
  "generated_at": "",
  "transaction": {},
  "asset": {},
  "jurisdiction": {},
  "entity": {},
  "ownership": {
    "legal_owner": {},
    "beneficial_owners": [],
    "cap_table": [],
    "transfer_restrictions": []
  },
  "participants": [],
  "documents": [],
  "requirements": [],
  "approvals": [],
  "exceptions": [],
  "audit_events": [],
  "readiness": {
    "overall_score": 0,
    "status": "",
    "categories": {}
  }
}
```

Every extracted or verified data point should support provenance:

```json
{
  "value": "",
  "source_type": "user_entered | document_extracted | adviser_reviewed | system_generated",
  "source_document_id": "",
  "confidence": null,
  "verified_by": null,
  "verified_at": null
}
```

Do not embed legal conclusions in the manifest.

# 14. Remove or correct misleading elements

The following current behavior must be corrected:

* A hotel refinance description should not classify as a Business Acquisition.
* A workspace classified as Business Acquisition should not generate property-specific documents unless the asset description supports them.
* The preview configuration and activated workspace must use the same pack data.
* Workspace name must not receive an unexplained random suffix.
* Jurisdiction should not be shown as an issuance regime when the transaction itself is not configured for digital asset preparation.
* “Transaction risk: Low” must not appear when no documents or participants have been added.
* Zero open blockers is not the same as low transaction risk.
* The activated workspace must preserve the stages, participants, and documents shown in preview.

These consistency issues are higher priority than advanced tokenization integrations because they affect user trust.

Do not begin native token minting, wallets, subscriptions, payments, custody, or trading in these phases.

# Acceptance criteria

The implementation is complete when:

1. An ordinary transaction can operate exactly as it does today without seeing unnecessary tokenization fields.
2. A user can enable Digital Asset Readiness for any appropriate transaction type.
3. The selected jurisdiction adds specific, configurable preparation requirements.
4. Ownership and beneficial ownership can be captured with supporting evidence.
5. Every readiness percentage is traceable to individual requirements.
6. Missing requirements automatically create actionable tasks.
7. Documents visibly contribute to relevant readiness categories.
8. The activated workspace exactly matches the approved preview configuration.
9. At closing, the user can generate a Verified Digital Asset Package.
10. The package includes human-readable exports and a structured JSON manifest.
11. The UI never implies that Kontra has approved, issued, sold, custodied, or legally cleared a token.
12. No blockchain transaction is required for the feature to provide value.

---

## Final product principle

Kontra should not add tokenization as a disconnected feature.

Kontra should make the transaction itself produce a verified and structured digital asset record.

The intended product progression is:

> Coordinate → Collect → Analyze → Verify → Structure ownership → Prepare → Export

Not:

> Upload documents → Mint token

The current platform should remain the foundation. This is an additive Digital Asset Layer, not a full rebuild.
