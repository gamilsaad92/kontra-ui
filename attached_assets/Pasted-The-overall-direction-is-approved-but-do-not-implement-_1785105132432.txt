The overall direction is approved, but do not implement or run the migration yet. Please revise the proposal to address the following issues first.

1. Add role- and participant-level document authorization. The current participant policy gives every active participant access to every document in the room. RLS and download authorization must verify whether each document is visible to all participants, selected roles, or selected individuals. Apply the same restrictions to document versions, AI analysis, findings, comments, tasks, uploads, and activity records.

2. Correct the invitation and OTP sequence. Creating an invitation should send only the unique invitation link. Opening that link should validate the token and allow the participant to request an OTP at the invited email. After Supabase verifies the OTP and creates an authenticated session, an authenticated acceptance operation must confirm that the verified user email matches invited_email before creating the participant record.

3. Do not use auth.admin.generateLink as though it automatically sends the OTP unless a custom email provider is intentionally handling delivery. Document the exact Supabase Auth calls and email templates that will be used.

4. Do not query deal_rooms anonymously to determine whether auth_v2_enabled is active. The invitation-resolution Edge Function should determine the correct flow internally and return only safe display information.

5. Choose one Storage model. For Kontra, use a private bucket with an authenticated get-document-url Edge Function that checks room membership and document-level visibility, logs the event, and returns a 60-second signed URL. Do not also grant broad participant Storage SELECT access if signed URLs are the only intended access path.

6. Do not apply a blanket REVOKE ALL against storage.objects without first reviewing existing Storage grants and policies. Changes must be limited to the deal-room-documents bucket and tested against existing owner uploads and downloads.

7. Treat enabling RLS as a behavior-changing migration, even while the feature flag is false. Before enabling RLS, verify that every existing room has the correct owner_uid and that every current owner query carries a valid authenticated JWT. Test all existing owner operations in staging before changing production policies.

8. Replace the proposed rollback that disables RLS. A rollback must restore the exact prior policies, grants, and RLS state. Export the current policies and grants before migration. Do not use DROP TABLE ... CASCADE as the default production rollback.

9. Make the security audit log application-immutable by blocking UPDATE and DELETE through database permissions and triggers. Do not expose a general audit-write endpoint directly to the browser.

10. Normalize invited_email and require the authenticated user’s verified normalized email to match it when accepting the invitation.

11. Add indexes supporting every RLS EXISTS condition and token lookup.

12. Make invitation acceptance atomic so that participant creation, invite acceptance, and audit logging either all succeed or all fail. Prevent the same invitation from being accepted concurrently.

13. Confirm whether one person may hold more than one role. UNIQUE(property_id, auth_uid) currently prevents that.

14. Document revocation accurately: new database access and new downloads are blocked immediately, but a previously generated 60-second signed URL remains usable until it expires.

Please return the revised schema, exact RLS policies for role-based document access, Storage policy design, exact Auth/OTP sequence, migration up and down scripts, and test matrix. After those are reviewed, proceed only in staging and enable the flag for one internal room.
