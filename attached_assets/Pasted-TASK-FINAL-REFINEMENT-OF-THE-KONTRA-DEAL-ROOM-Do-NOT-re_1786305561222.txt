TASK: FINAL REFINEMENT OF THE KONTRA DEAL ROOM

Do NOT redesign the application from scratch.

The current structure is substantially correct:
- Overview
- Documents
- People
- Kontra AI floating assistant / side drawer
- Digital Asset Readiness
- Existing Kontra visual design system

This task is a SURGICAL PRODUCT/UX REFINEMENT.

Do not remove tokenization / digital-asset preparation.
Do not add an Activities tab.
Do not add a separate Tokenization tab at this stage.
Do not add unnecessary dashboard widgets.
Do not duplicate information between tabs.
Do not change the global navigation.
Do not remove the AI assistant.
Do not fundamentally redesign Documents or People.

The main objective is:

Make the Deal Room feel like an intelligent transaction operating system that progressively organizes a real-world transaction and prepares its verified transaction record for eventual digital-asset/tokenization workflows.

==================================================
1. PRODUCT MODEL — IMPORTANT
==================================================

Kontra has TWO connected layers:

LAYER 1 — TRANSACTION EXECUTION

The Deal Room helps users:
- collect documents
- coordinate participants
- identify missing information
- extract structured facts
- surface inconsistencies and exceptions
- understand what is blocking the transaction
- track progress
- maintain an auditable transaction record

LAYER 2 — DIGITAL ASSET / TOKENIZATION READINESS

As Layer 1 becomes complete, Kontra progressively organizes the information that may later be needed to prepare the transaction/asset for a digital-asset or tokenization workflow.

DO NOT eliminate this second layer.

However:

Kontra must NOT imply that simply uploading documents automatically makes an asset legally tokenizable.

The product should distinguish between:

"transaction information readiness"

and

"legal/regulatory approval for issuance."

Kontra can organize and prepare information for tokenization.

Kontra should NOT claim that it has legally approved an issuance unless a future regulated workflow explicitly does so.

5. FIX "WHAT NEEDS ATTENTION"
==================================================

This is the most important change.

The current empty state says:

"Nothing urgent right now"

and

"Nothing needs your attention right now."

THIS IS WRONG when the room contains no documents and no participants.

An empty transaction absolutely requires action.

The system must distinguish between:

A. EMPTY / NOT STARTED
B. ACTIVE / NO BLOCKERS
C. ACTIVE / ACTION REQUIRED
D. BLOCKED / HIGH PRIORITY

--------------------------------
STATE A — EMPTY ROOM
--------------------------------

If there are no documents and/or the transaction has not been initialized:

Heading:

"Start this transaction"

Subtext:

"Add the first documents and participants so Kontra can begin building the transaction record."

Show contextual actions:

Upload first document
Invite participant

Optionally show 2–3 concrete initialization tasks:

• Upload core transaction documents
• Invite the deal owner / relevant parties
• Confirm basic transaction information

DO NOT say:
"Nothing urgent right now."

--------------------------------
STATE B — ACTIVE, NO BLOCKERS
--------------------------------

Only after the transaction has actual activity/data should the system be allowed to say:

"Nothing requires your attention right now."

Supporting text:

"Kontra is monitoring the transaction for missing information, inconsistencies, participant requests, and upcoming actions."

--------------------------------
STATE C — ACTION REQUIRED
--------------------------------

Display only meaningful items.

Example:

WHAT NEEDS ATTENTION

3 items require action

Financial Statements
Missing · Waiting on Seller
[Request]

Purchase Agreement
Missing · Legal Advisor
[Request]

Buyer identity
Needs confirmation
[Review]

Do NOT duplicate the complete Documents checklist here.

Maximum approximately 3–5 priority items.

Provide:

"View all in Documents →"

when appropriate.

--------------------------------
STATE D — BLOCKER
--------------------------------

High-priority blockers should visually rise above routine missing items.

Example:

BLOCKING TRANSACTION

Title report contains inconsistent ownership information.

Kontra found different owner names across:
- Purchase Agreement
- Title Report

[Review finding]

Use restrained visual emphasis.

Do NOT make the entire dashboard red.

→ Digital Asset Preparation
