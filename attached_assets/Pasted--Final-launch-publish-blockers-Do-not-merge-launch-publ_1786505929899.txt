## 2. Canonicalize AI-extracted Transaction Record keys

Extraction currently produces valid facts under noncanonical keys such as:

`asset_identity.legal_name`

`transaction.target_closing_date`

These do not map to the required readiness schema and therefore valid extracted data can be ignored by Transaction Readiness.

Do not solve this by adding duplicate required fields.

Create or use one canonical field-mapping layer between AI extraction output and the Transaction Record schema.

Requirements:

* equivalent concepts resolve to one canonical Transaction Record key,
* no duplicate facts are created under aliases,
* provenance is preserved,
* extracted status is preserved,
* confirmed status is preserved,
* required-field readiness uses the canonical key only.

Examples:

`transaction.target_closing_date` → canonical closing-date field

`asset_identity.legal_name` → canonical asset/company legal-name field

The canonical mapping must be workflow-pack aware where necessary, but the same real-world fact must not exist simultaneously under multiple aliases.
