Implement an additive “AI Room Generator” for Kontra.

IMPORTANT:
- Do NOT replace or refactor the existing workflow-pack system.
- Do NOT break existing room creation.
- Existing template-based room creation must continue to work exactly as it does today.
- The AI-generated workflow becomes another way to create a room.
- Reuse the current document, checklist, participant, task, workflow, transaction record, Operations Manager, permissions, and room infrastructure wherever possible.

GOAL

Allow a user to describe a transaction in natural language.

Examples:

“Freddie Mac hazard loss for a multifamily property. Fire damaged 12 units. Insurance proceeds are being held by the servicer. Borrower has already advanced funds and is requesting reimbursement.”

“Sale of a multifamily property in California being marketed by CBRE. Buyer will obtain agency financing.”

“$15M business acquisition. Buyer is acquiring assets rather than stock, financing includes an SBA loan, closing targeted in 45 days.”

Kontra should analyze the description and generate a transaction-specific proposed room rather than loading a generic workflow.

2. TRANSACTION INTELLIGENCE PIPELINE
==================================================

Create a central server-side service:

transactionRoomGenerator

Suggested location:
server/services/transactionRoomGenerator.js

Do not allow the frontend to independently construct the workflow.

Pipeline:

A. Parse transaction description
B. Classify transaction
C. Identify relevant entities/context
D. Retrieve applicable internal Kontra templates
E. Retrieve relevant authoritative/public sources when research tools are available
F. Generate structured proposed workflow
G. Validate output
H. Return proposal to user
I. User reviews/modifies
J. User approves
K. Existing Kontra infrastructure creates the room

==================================================
4. SOURCE / PROVENANCE MODEL
==================================================

Every AI-created requirement must explain where it came from.

Use these classifications:

AUTHORITATIVE
Requirement supported by regulator, agency, lender, government, investor, or other authoritative source.

UPLOADED
Requirement derived from a document uploaded by the user.

TEMPLATE
Requirement inherited from an existing Kontra workflow/template.

AI RECOMMENDATION
Suggested by Kontra based on transaction context but not represented as a formal external requirement.

Never present an AI recommendation as a legal, regulatory, Freddie Mac, Fannie Mae, lender, CBRE, or other third-party requirement unless a source actually supports it.

Store provenance with the requirement.

==================================================
5. RESEARCH ARCHITECTURE
==================================================

Create a provider-neutral interface such as:

researchTransactionContext({
  description,
  entities,
  jurisdiction,
  transactionType
})

The room generator should NOT be tightly coupled to one search vendor.

The research layer should support:

- web/public source search
- authoritative-domain prioritization
- supplied/uploaded documents
- existing Kontra templates
- future private knowledge bases

Source priority:

1. Transaction-specific uploaded documents
2. Organization-provided requirements
3. Regulatory / agency / investor authoritative sources
4. Existing Kontra templates
5. Other credible public sources
6. AI recommendations

For V1, if external research is unavailable, generate from templates/context but clearly mark unsupported requirements as AI_RECOMMENDATION.

Never fabricate citations.

==================================================
6. IMPORTANT ORGANIZATION BEHAVIOR
==================================================

Entity names must be treated carefully.

Example:

“Sale by CBRE”

Kontra may identify:
organization = CBRE
role = broker/advisor

But Kontra must NOT claim something is “required by CBRE” unless Kontra retrieved an actual CBRE source or the user supplied a CBRE document.

Same treatment for Freddie Mac, Fannie Mae, banks, law firms, title companies, brokers, insurers, etc.

Do NOT allow create-room to accept unvalidated arbitrary AI output directly.

==================================================
11. AI SAFETY / RELIABILITY
==================================================

The AI must never silently invent requirements.

Implement:

- schema validation
- source classification
- confidence values
- unsupported-claim detection
- URL/reference validation where applicable
- duplicate requirement detection
- deterministic normalization of stage/requirement keys

When uncertain, AI should create an “issue_to_confirm” rather than pretending to know.

Example:

Instead of:
“Freddie Mac approval required.”

Use:
“Confirm whether Freddie Mac approval is required for this loss scenario.”

unless retrieved evidence supports the first statement.

==================================================
12. OPERATIONS MANAGER INTEGRATION
==================================================

After room creation, include the generated transaction context in Operations Manager grounding.

Operations Manager should know:

- why the room was created
- transaction type/subtype
- entities
- jurisdiction
- source-backed requirements
- AI recommendations
- unresolved assumptions

It should be able to answer:

“Why do we need this document?”

“This requirement came from [source].”

“What still needs to be confirmed?”

“Can we remove this requirement?”

But removing requirements must still use existing permission/authorization rules.
