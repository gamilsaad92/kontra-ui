Proceed with Sprint 1 implementation based on the audit findings.

Do not create a parallel agent architecture. Extend the existing Kontra systems and preserve current public API compatibility.

The canonical architecture for this work is:

Verified Room Access → Normalized Transaction Context → Existing Document Extraction → Canonical Transaction Record → Central Transaction-State Recalculation → deal_room_tasks → Human Approval Gateway → Durable Audit → Overview/Operations Manager

Implement in the following order.

1. Establish canonical boundaries

Treat these as architectural rules:

* transaction_record_fields remains the canonical structured transaction data layer.
* Workflow packs remain authoritative for roles, requirements, stages, documents, and readiness expectations.
* deal_room_tasks becomes the canonical operational issue/action layer.
* Operations Manager becomes the foundation for the future Kontra Transaction Agent.
* Transaction Record approvals remain separate from operational task/action approvals.
* Settlement remains deterministic, provider-neutral readiness logic.
* Legacy loan-servicing agents remain isolated from deal-room agent behavior.

Do not introduce agent_findings, issues, agent_tasks, transaction_record_conflicts, or another approval system during Sprint 1 unless implementation proves that the existing models cannot support the requirement.

2. Fix room/org/actor authorization first

Before enabling agent actions, create one verified room access context carrying:

propertyId
roomId
actorId
actorType
role

stageKey

Validate organization membership, room/property relationship, participant role, invite/token access, and operation permissions.

Specifically address the audit findings around:

* email-based room discovery
* /api/public/* organization-context bypass
* caller-selected X-Org-Id
* participant mutation authorization
* cross-room/cross-org access

Do not break legitimate invite-link participant access while fixing this.

Every related event should carry the same correlation ID.

* resolve current stage
* read canonical Transaction Record fields
* read confirmation/not-applicable states

Invoke it after:

* successful document extraction
* Transaction Record PATCH
* field confirmation
* field not-applicable changes
* metadata synchronization
* checklist changes
* participant changes
* relevant stage changes
* settlement-mode changes where applicable

Do not create another readiness algorithm.

Why this is the right next move

There are really two different things happening here.

The original idea was:

“Let’s add AI agents to Kontra.”

The audit discovered that Kontra already contains the beginnings of that architecture. The real problem is that they aren’t connected consistently:

Document Analysis
↕
Transaction Record
↕
Task Engine
↕
Readiness
↕
Operations Manager
↕
Overview

Sprint 1 makes those into one system.

Once that works, adding the actual specialized agents becomes much easier.

Then Sprint 2 can be:

Document Agent → Diligence Agent → Financial Agent → Legal Agent

And Sprint 3:

Kontra Transaction Agent → recommended actions → approval → execution

That sequence is much safer than creating six new AI agents now.

There’s also one audit finding I would not treat as a minor cleanup item: the authorization findings. Before Kontra starts letting AI recommend or eventually execute transaction actions, the room/org/participant authorization layer needs to be dependable. Otherwise agentic functionality magnifies an existing access-control weakness.
