This revision is much closer, but it is not approved for implementation yet. Please make the following final corrections before writing or running the migration.

1. Correct the OTP implementation. auth.admin.generateLink does not automatically send an OTP through Supabase SMTP. Either use signInWithOtp after the invite token is validated, or use generateLink and send the returned OTP yourself through Resend. Do not describe generateLink as an email-sending operation.

2. Remove invite_token_hash from Auth user metadata and JWT data. It is unnecessary and should not be persisted on the user account. The invitation token and authenticated identity must be validated separately during acceptance.

3. Implement invitation acceptance as a real database transaction. Multiple supabase-js Data API calls from an Edge Function do not form one transaction merely because BEGIN and COMMIT appear in the design. Use a tightly scoped private database RPC or a direct pooled PostgreSQL transaction.

4. Change the document visibility default from all_participants to owner_only. Add owner_only to the allowed values. Existing documents must be backfilled as owner_only unless the owner explicitly shares them.

5. Do not make auth_v2_enabled=false restore insecure legacy participant access. When v2 is disabled, the owner flow may continue, but external participant access must remain disabled until that room is securely migrated.

6. Replace the one-role-per-email limitation. One authenticated participant must be able to hold multiple roles through a deal_room_participant_roles junction table. Do not require a person to use multiple email addresses.

7. Validate incoming participant JWTs with Supabase Auth and use the verified user.id and user.email. Do not merely decode and trust incoming JWT claims.

8. Correct the token description. The raw token necessarily appears in the participant’s browser URL, but it must never be stored plaintext in the database or returned in API responses. Add Referrer-Policy: no-referrer, Cache-Control: no-store, token redaction from logs, no third-party analytics on the invite screen, and replace the URL after resolution.

9. Add server-side OTP request limits by invite, email, and IP, with a resend cooldown and generic responses that do not reveal whether an invite or email exists.

10. Rotate the invitation token whenever an invitation is reissued. Accepted, revoked, expired, and superseded tokens must never be reusable.

11. Expand the rollback snapshot to include policy roles, permissive/restrictive mode, schemas, RLS and FORCE RLS state, table grants, Storage policies, function grants, and exact executable policy definitions. Test the complete down migration in staging.

12. Rename document_downloaded to signed_url_issued or document_download_authorized because the event is recorded when the URL is generated, not when Storage confirms the actual download.

13. Correct the test wording: clearing browser storage removes the local authenticated session; it does not revoke the participant’s server-side access.

After these corrections, provide the final migration schema, exact Auth sequence, transactional acceptance implementation, RLS policy definitions, rollback scripts, and staging test output. Do not modify the production database or live participant flow before that review.
