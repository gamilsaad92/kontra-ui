Replit Implementation Instructions — Kontra Agentic Transaction Architecture

Objective

Evolve Kontra from a workspace that analyzes documents into an agentic transaction operating system.

The new architecture should follow this flow:

Documents → Transaction Record → Specialized Agents → Transaction Agent → Human Approval → Actions

Do not redesign the entire UI or create a separate page full of AI agents.

The agent system should primarily operate behind the existing workspace. Users interact with one main Kontra Transaction Agent, while specialized agents work in the background.

Preserve the existing Transaction Record, confirmation/audit logic, workflow packs, settlement architecture, document upload flow, and activity history.

⸻

PHASE 1 — BUILD THE AGENT FOUNDATION

Task 1 — Create a shared agent architecture

Create a new backend module:

server/services/agents/

Suggested structure:

server/services/agents/
  transactionAgent.js
  documentAgent.js
  financialAgent.js
  legalAgent.js
  diligenceAgent.js
  settlementAgent.js
  agentRouter.js
  agentContext.js
  agentActions.js
  agentAudit.js

Do not duplicate document-processing logic that already exists.

Existing extraction, document classification, financial analysis, legal analysis, transaction-record mapping, settlement readiness, and workflow logic should be exposed as tools/functions that agents can call.

⸻

Task 2 — Create the Agent Context

Create:

agentContext.js

Every agent must receive the same normalized transaction context.

Example:

{
  transactionId,
  workspaceType,
  workflowPack,
  currentStage,
  participants: [],
  documents: [],
  transactionRecord: {
    fields: [],
    confirmedFields: [],
    unresolvedFields: [],
    conflicts: []
  },
  requirements: [],
  issues: [],
  activity: [],
  settlement: {
    mode,
    readiness,
    conditions
  }
}

The context must always use canonical Transaction Record keys.

Do not allow aliases such as:

transaction.value
financial.purchase_price
purchasePrice

to appear as separate facts if they represent the same canonical field.

Use the canonicalization work already implemented in transactionRecordSchema.js.

⸻

PHASE 2 — SPECIALIZED AGENTS

Task 3 — Document Agent

Create:

documentAgent.js

Responsibilities:

1. Detect document type.
2. Run existing document extraction.
3. Extract structured facts.
4. Map those facts to canonical Transaction Record fields.
5. Identify which checklist/requirements the document satisfies.
6. Detect conflicting values.
7. Identify missing expected information.
8. Return a structured result.

Example output:

{
  "documentType": "purchase_agreement",
  "confidence": 0.97,
  "extractedFields": [
    {
      "key": "transaction.purchase_price",
      "value": 4250000,
      "confidence": 0.99,
      "source": {
        "documentId": "123",
        "page": 4
      }
    }
  ],
  "requirementsSatisfied": [
    "executed_purchase_agreement"
  ],
  "conflicts": [],
  "warnings": []
}

The Document Agent must not automatically overwrite confirmed Transaction Record values.

Confirmed fields remain protected.

⸻

Task 4 — Financial Agent

Create:

financialAgent.js

Responsibilities:

* Analyze uploaded financial information.
* Use existing financial-analysis functions.
* Calculate transaction-specific metrics.
* Compare numbers across documents.
* Detect material inconsistencies.
* Identify missing financial information.
* Update proposed Transaction Record values.
* Generate concise findings.

Examples:

Purchase price differs between Purchase Agreement and Amendment #2.
Trailing-12 NOI is 8.4% below underwriting.
Debt service coverage cannot be calculated because annual debt service is missing.

Do not create speculative financial conclusions.

Every finding should reference its source data.

⸻

Task 5 — Legal Agent

Create:

legalAgent.js

Responsibilities:

Extract and analyze transaction-specific legal information such as:

* parties
* execution status
* effective dates
* closing dates
* termination dates
* contingencies
* notice requirements
* assignment rights
* obligations
* signatures
* amendments
* closing conditions

The Legal Agent must remain document intelligence, not legal advice.

UI language should say:

AI-assisted legal review

Avoid:

Legal opinion

or:

Legal determination

⸻

Task 6 — Due Diligence Agent

Create:

diligenceAgent.js

Responsibilities:

Evaluate the transaction requirements generated by the workflow pack.

For every requirement determine:

SATISFIED
PARTIALLY_SATISFIED
MISSING
CONFLICT
EXPIRED
REQUIRES_CONFIRMATION
NOT_APPLICABLE

Example:

{
  "requirement": "Insurance Certificate",
  "status": "PARTIALLY_SATISFIED",
  "reason": "Certificate received but policy expires before scheduled closing.",
  "sourceDocumentId": "abc123"
}

The Due Diligence Agent should feed the existing:

Issues & Exceptions

system.

Do not build another duplicate issues system.

⸻

Task 7 — Settlement Agent

Extend the settlement architecture already implemented.

Create:

settlementAgent.js

Settlement modes remain:

traditional
digital
tokenized

The agent should evaluate readiness based on the selected mode.

Example result:

{
  "mode": "tokenized",
  "readiness": 61,
  "conditions": [
    {
      "name": "Entity verification",
      "status": "complete"
    },
    {
      "name": "Jurisdiction determination",
      "status": "missing"
    }
  ]
}

Important:

The Settlement Agent evaluates readiness only.

Kontra must not represent itself as:

* custodian
* broker-dealer
* securities exchange
* transfer agent
* escrow holder
* legal adviser

unless future integrations actually support those services through properly authorized providers.

PHASE 3 — TRANSACTION AGENT

Task 8 — Build the master Transaction Agent

Create:

transactionAgent.js

This becomes the primary intelligence layer for the transaction.

The Transaction Agent should orchestrate specialized agents rather than duplicating their logic.

Example request:

What's blocking this transaction?

The Transaction Agent determines that it needs:

Diligence Agent
Legal Agent
Settlement Agent
Transaction Record
Workflow requirements

Then synthesizes the answer.

Example response:

This transaction is currently 68% ready for closing.
3 items require attention:
1. Insurance coverage expires before closing.
2. Environmental reliance language has not been confirmed.
3. Purchase price conflicts with Amendment #2.
Recommended next action:
Request an updated insurance certificate.

⸻

Task 9 — Add an agent router

Create:

agentRouter.js

The router determines which specialized agents should run.

Example:

routeAgentRequest({
  userMessage,
  transactionContext
})

Possible result:

{
  "agents": [
    "diligence",
    "legal"
  ],
  "reason": "Question relates to closing blockers."
}

Do not call every agent for every question.

Only use relevant agents.

⸻

Task 11 — Human approval must remain mandatory

Agents must not silently perform material transaction actions.

Require human approval before actions such as:

* sending email
* changing confirmed Transaction Record values
* changing transaction stage
* marking major requirements complete
* changing settlement mode
* sealing the transaction
* generating final settlement instructions

Use the existing owner/coordinator authorization model.

The flow should be:

Agent recommends action
↓
User reviews
↓
Approve / Reject
↓
Action executes
↓
Activity log records action

PHASE 5 — FIX THE DOCUMENT → OVERVIEW PIPELINE

Task 12 — Make uploads automatically propagate through the workspace

This is critical.

Current problem:

Documents can be successfully analyzed but the Overview and transaction status do not update.

Replace the disconnected processing with an event-driven pipeline.

After every successful document analysis:

DOCUMENT_UPLOADED
↓
DOCUMENT_ANALYZED
↓
TRANSACTION_RECORD_PROPOSED_UPDATE
↓
REQUIREMENTS_RECALCULATED
↓
ISSUES_RECALCULATED
↓
READINESS_RECALCULATED
↓
TRANSACTION_AGENT_REVIEW
↓
OVERVIEW_REFRESH

Create one central function such as:

recalculateTransactionState(transactionId)

This should rebuild derived transaction state from authoritative data.

Do not require a page refresh to see updates.

PHASE 12 — SAFETY / RELIABILITY RULES

Implement these globally.

Rule 1

AI-generated values are proposals until confirmed where confirmation is required.

Rule 2

Confirmed Transaction Record fields cannot be overwritten by AI.

Rule 3

AI must cite the source document for material extracted facts.

Rule 4

AI must distinguish:

fact
inference
recommendation

Rule 5

If information is unavailable, say:

Not enough information available.

Never fabricate.

Rule 6

Critical actions require human approval.

Rule 7

Every important AI decision must be auditable.

PHASE 17 — IMPORTANT UI PRINCIPLE

The workspace should feel simpler after this implementation, not more complicated.

Do not expose internal architecture unnecessarily.

The user should feel like Kontra has one intelligent transaction coordinator.

Behind that interface:

Document Agent
Financial Agent
Legal Agent
Diligence Agent
Settlement Agent

can collaborate.

The front-end experience should primarily be:

Kontra Transaction Agent
Here's where the transaction stands.
Here's what changed.
Here's what needs attention.
Here's what I recommend doing next.

⸻

FINAL PRODUCT PRINCIPLE

Kontra should no longer merely say:

Your document was analyzed.

It should be able to say:

I analyzed the Purchase Agreement.
I identified 14 transaction facts.
8 requirements are now satisfied.
2 values require confirmation.
1 conflict was detected.
Closing readiness increased from 42% to 57%.
The highest-priority remaining issue is the insurance certificate,
which expires before the scheduled closing date.
I recommend requesting an updated certificate.
[Review Action]

That is the behavior we want throughout Kontra.

Do not replace the existing architecture.

Build the agent system on top of the Transaction Record, workflow packs, requirements, settlement capability system, document analysis, and audit structure already implemented.

The Transaction Record remains the canonical transaction data layer.

The agents reason over it.

Humans control material decisions.

Kontra coordinates the transaction.
